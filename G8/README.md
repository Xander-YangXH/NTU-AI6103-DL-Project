# G8 · EVA-generic

H4 的任务无关一端：EVA 初始化的校准数据换成通用语料（wikitext-103），其余和 G3 完全相同。

> **一句话结论**：通用语料算出的 EVA 子空间和任务数据算出的只有 0.64–0.74 重合，但全量数据上的精度和 G1、G3 基本一样（9 个配对比较里只有 MRPC 的 G8 − G3 = −0.91 显著）。低资源下 G8 介于两者之间：比 G3 高 1.08（不显著），比 G1 低 1.56（显著）。也就是说，激活里的"任务内容"对 EVA 的贡献很小。

### 解读

1. **子空间变了，精度基本没变。** 通用语料让每层约 30% 的主方向和 G3 不同，rank 分配也只挪动了 3–6% 的 rank（L1 距离 36–64，每挪一个 rank 计 2），层间的分配模式基本相同，但全量数据上 G8 和 G1 的差全部不显著。这和 G9 的结论一致：EVA 的激活子空间带的任务信息，不是精度的来源。
2. **MRPC 上的 −0.91 要谨慎看。** 区间不含 0，但它主要来自 G8 的方差很小（sd 0.34），而且这里一共做了 11 个比较、没有校正。RTE 的 G8 − G9 = −3.61 也一样：RTE 本身就不稳定（见 `summary/SUMMARY.md` §2 第 7 条）。两者都待验证，比如加种子。
3. **低资源下，任务数据校准的 EVA 反而更差。** G3 比 G1 低 2.64；G8 只低 1.56，G8 − G3 = +1.08，区间刚好碰到 0。用任务数据校准不但没有帮助，还可能是 EVA 在低资源下吃亏的一部分原因（待验证）。
4. **初始梯度更大，并不带来更高精度。** G8 在 MRPC、RTE 上第 0 步梯度比 G3 大 1.4–1.7 倍，精度却略低，和团队"初始梯度大小不决定精度"的发现一致。
5. **格式可能比内容更决定子空间（待验证）。** G8 保留了 G3 的 token 排布，只换内容，和 G3 的重合（0.64–0.74）**高于** G9 用真实的另一任务数据。差距在格式变了的 SST-2 上最大（G8 0.64 vs G9 0.48–0.51）；在格式相同的 MRPC/RTE 上很小（G8 0.68–0.74 vs G9 0.64–0.68）。G9 的 SST-2 换任务时，格式（单句 → 句对）和长度也一起变了，所以它较低的重合里，有一部分可能来自格式而不是任务内容。要分开这两个因素，需要一个排布不同的 G8 变体，或一个排布匹配的 G9。

## 设计：和共享管线的关系

`src/data.py`、`src/alloc.py`、`src/init_g34.py`、`jobs/run_queue.sh` 是 `yinchenyu_g3g4` 分支（commit 2661637）中 `G3G4/` 的**原样拷贝**。`src/train.py` 也是从那里拷贝的，只改了一处：

- **G3**：`data.calib_loader`，从训练集随机抽 1,024 条，batch 16。
- **G8**：`generic.generic_calib_loader`。
  - 用同一个种子抽**同一批** 1,024 条，保留每条的 token 排布：总长度、单句/句对格式、两段各自的长度。
  - 只把段内的 token 换成连续的 wikitext-103 文本。
  - DataLoader 用同一个生成器打乱，所以 G8 第 i 个 batch 的形状和 G3 第 i 个 batch 完全一样。

这样 G3 和 G8 的差别只剩"校准内容是不是任务数据"。`tests/test_generic.py` 会核对这一点：长度、attention mask、特殊 token 位置全部相同，段内 token 和 G3 重合不到 1%。

其余全部沿用共享设置（主 README 第 4 节）：

- 数据划分 `SPLIT_SEED = 2026`。
- 分类头预热 1 个 epoch，学习率 1e-3。
- r = 8，α = 8，ρ = 2，τ = 0.99；batch 32，max_len 128。
- epoch 数：SST-2 3、MRPC 10、RTE 10。
- 种子：SST-2 0–2，MRPC / RTE 0–4。
- 取最后一个 epoch，在官方 validation 上评估一次。
- 学习率沿用 G3 选出的值：SST-2 1e-3，MRPC 2e-4，RTE 2e-4（来自 `G3G4/results/chosen_lr.json`）。

结果 JSON 的字段和 G3 相同，另加 `calib`。初始 A 保存在 `cache/g8A_{task}_False_s{seed}.pt`，格式和 G3 的 `g3A_*` 相同。

## 在 TC2 上运行

目录布局和 G3G4 一样：代码放在 `~/某目录/G8`，数据放在同级的 `~/某目录/gweva-data`。

**1. 环境和数据**（登录节点，需要联网，约 15–30 分钟）

```bash
cd G8 && bash jobs/setup.sh
```

脚本会新建 conda 环境 `gweva`，版本和 G3 一致（torch 2.11.0+cu128、transformers 5.21.0、peft 0.21.2、datasets 5.1.0）。然后把 roberta-base、GLUE 三个任务和 wikitext-103 存到 `../gweva-data`。

如果要复用已有的环境，用 `CONDA_ENV=环境名 bash jobs/setup.sh`；后面提交作业时也要带上同一个 `CONDA_ENV`。

**2. 一次提交，跑完全部**

```bash
sbatch --export=ALL,STAGE=all,NPAR=2 jobs/g8.sbatch
```

这个作业会依次跑：

- **main**：提案里 G8 的 13 次（SST-2 3 个 seed，MRPC / RTE 各 5 个）；
- **lowres**：低资源 SST-2 1k 子集 5 次，是可选扩展，设置和 G3 的 lowres 阶段完全相同；
- 最后自动把结果 JSON、`cache/g8A_*` 和日志打成 `g8_all_<jobid>.zip`，**把这个 zip 发回来就行**。

G3 同样的 13 次在 A40 上逐个跑合计约 45 分钟；lowres 每次只有约 600 步。整个作业预计 1 小时左右。已完成的运行会自动跳过，超时或中断后重新提交同一条命令即可继续。

想先确认环境能跑通，可以先跑 1 次 RTE（约 3 分钟）：

```bash
sbatch --export=ALL,STAGE=pilot,NPAR=1 jobs/g8.sbatch
```

lowres 超出了提案范围。它要回答的问题是：低资源下 G3 显著低于 G1（−2.64 个百分点），那么用通用语料初始化的 G8 更像 G3 还是更像 G1？只想跑提案内容的话，用 `STAGE=main`。

## 汇总（本地）

```bash
python jobs/summarize.py --g3_cache 解压后的/G3G4_cache/cache
```

脚本会输出 G8 和 G3 的同种子配对差（95% CI，t 分布；有 lowres 结果时也会输出 lowres 的配对差）、第 0 步 ‖∂L/∂B‖，以及 G8 与 G3 初始 A 的子空间重合度和 rank 分配 L1 距离。结果写到 `results/g8_summary.txt` 和 `results/g8_runs.csv`。G3、G1 的参照 JSON 直接从仓库里的 `../G3G4/results`、`../G1G2/results` 读取（仓库外用 `ref/G3/` 里的拷贝）。
